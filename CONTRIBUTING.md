# Contributing

This repository builds one paper's empirical pipeline. Changes are welcome
if they keep the property the whole suite exists to protect: **every number
is reproducible, and a changed number is attributable to a named rule
change.**

## The rules that matter

1. **A methodology change is a profile change, not a code change.** Read
   [`docs/methodology-config.md`](docs/methodology-config.md) § 3 first.
   One YAML, one registration, regenerated fixtures, a diff to discuss.
2. **Test first.** New behaviour is written as a failing test, watched fail,
   then made to pass. A change without a test is not finished.
3. **Fixtures are the proof.** `tests/fixtures/` are regenerated by the
   scripts, never hand-edited; `docs/data/` measurement blocks are generated
   and spliced, never retyped.
4. **Both implementations agree.** Production (`delhi_psi/`) and the
   independent reference (`tests/reference_impl.py`) change together, with
   the same formula; the mapped-knob test is what keeps them in step.
5. **No notebooks.** The pipeline stages are the interface; figures and
   measurement tables are scripts.

## Running it

```bash
uv run pytest -q -W error          # the full gate
uv run delhi-psi --help            # preprocess / compute
```

The real-data tests skip without `DELHI_DATA_DIR` (default `~/delhi_data`);
CI runs the oracle suite, which needs no real data.

## Submitting a change

- One ticket per branch, a red-first test, and a PR whose body carries the
  spec/plan links and the blast radius (`git status --porcelain --
  tests/fixtures/` must show only intended files).
- CI must be green; the fixture drift guard regenerates every fixture and
  fails on any change that was not committed deliberately.
- Commit messages name the ticket (`feat(del-31): …`, `fix(del-64): …`).

## Scope

Open an issue before starting anything that changes a methodology value or
the index definition — those are decisions for the project's domain owner,
not implementation details.
